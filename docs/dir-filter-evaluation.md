# 目录筛选（无分隔符）可行性评估

> 结论先行：**不建议做自动目录筛选。** 体积代价可以接受（+4.3MB），但**算法无法判断用户指的是目录还是文件名片段**——实测会破坏已有正确结果，而收益只覆盖少数场景。建议改为**显式语法**（`/` 或新前缀），成本极低且无副作用。

## 1. 现状基线（真实 Chaos 工作区，51,266 条目）

| 组成 | 体积 |
|---|---|
| `path` 字符串 | ~9.1 MB |
| `pathLower` 字符串 | ~9.1 MB |
| `nameLower` 字符串 | ~2.3 MB |
| 对象形状 | ~3.1 MB（~64 B/条目） |
| **索引总计** | **~23 MB（约 460 B/条目）** |

字符串是大头（20.4 MB / 88%），因为 `pathLower` 是 `path` 的完整副本。这是当前索引的主要内存成本。

## 2. 候选结构的体积代价（实测，同一批条目）

| 结构 | 体积 | 每条目 | 评价 |
|---|---|---|---|
| 目录前缀字符串（每条目一份） | +2.0 MB | 40 B | 便宜，但只省一次 `lastIndexOf` |
| **目录名集合（2,801 个名字）** | **+4.2 MB** | 86 B | 便宜，够用于"这个片是不是目录名"判断 |
| 目录段倒排索引 `Map<段, 条目ids>` | +4.3 MB | 87 B | 便宜，可把目录筛选下推进候选选择 |
| basename trigram 倒排索引 | +9.4 MB | 193 B | 中等；12,386 个 trigram、109 万 posting |
| `segments[]`（每条目一个字符串数组） | +16.8 MB | 343 B | 偏贵，数组对象开销大 |
| joined 子词（每段一个 string） | +25.0 MB | 512 B | 贵 |
| **子词边界位图（每段一个 Uint8Array）** | **+108.3 MB** | **2,214 B** | **灾难**：51k×平均 4 段 = 20 万个 Uint8Array 对象，每个 ~100B 固定开销 |

**教训**：JS 里"每条目再挂一个小对象/小数组"的代价是**固定开销主导**（每对象 ~100 B），与内容长度几乎无关。51k 条目上挂 20 万个小对象就是 100+ MB。这类结构必须改成**扁平化的大 Int32Array + 偏移表**，否则不可用。

## 3. 功能实测：机制有效，但会误伤

机制：索引期收集目录名集合；查询片若命中某个目录名，就**强制它匹配目录部分**（留在 basename 里不算命中）。

| 查询 | 现状（v0.1 行为） | 强制目录后 | 判定 |
|---|---|---|---|
| `index.html ui` | ❌ 命中 `chaos_update_server_observer_index.html` | ✅ `_content/ui/coherent/bag/index.html` | **改善** |
| `index.html bag` | ❌ **0 结果** | ✅ `_content/ui/coherent/bag/index.html` | **改善** |
| `nsd _rpc` | ✅ | ✅ | 不变 |
| `game_scene lua` | ✅ `.../game_scene/chaos_game_scene.lua` | ❌ `...register_cpp_to_lua/game_scene.h` | **劣化** |
| `client module` | ✅ `client_module.h` | ❌ `chaos_plugin_template_module/Templates/...` | **劣化** |
| `material ast` | ✅ `material_asset_serializer.h` | ❌ `ui/coherent/material_tracking` | **劣化** |

延迟几乎无变化（4.6–12.1 ms，与现状 4.3–9.6 ms 同量级）。

**根本原因**：`lua` / `module` / `ast` 既是真实目录名，也是常见的**文件名片段**。强制它们匹配目录，等于把本来正确的查询劫持到错误结果上。

## 4. 为什么无法自动判定（歧义量化）

统计 2,801 个不同的目录段名，各自出现在多少个 basename 中：

| 目录名 | 作为目录出现的条目 | 出现在多少个 basename 中 |
|---|---|---|
| `lua` | 199 | **2,981** |
| `client` | 7,634 | **2,526** |
| `ui` | 9,562 | **1,588** |
| `manager` | 74 | **2,718** |
| `module` | **4** | **539** |
| `ast` | **3** | **618** |
| `bag` | 6 | 37 |
| `wolfgang` | 13,473 | **0** |

**关键统计**：
- **只有 3 个（0.1%）目录名不出现在任何 basename 中** —— 几乎没有"天然无歧义"的目录名
- **608 个（21.7%）出现在 ≥20 个 basename 中**，属高度歧义
- `module` / `ast` 的**歧义比超过 100:1**（3–4 个目录 vs 539–618 个 basename）

结论：**不存在一条阈值规则能区分"用户想筛目录"和"用户想筛文件名"。** `ui`/`bag` 看起来安全（比值高），但 `bag` 仍出现在 37 个 basename 中；而真正好用的短词（`lua`/`client`/`module`）恰恰最歧义。

## 5. 建议

### 5.1 不做自动目录筛选（推荐）

理由：收益只覆盖"第二个词恰好是目录名且不在 basename 中"的场景，但代价是**破坏原本正确的查询**——这是净负收益。而且**完全无法靠调参修复**（§4 证明歧义不可分）。

### 5.2 改为显式语法（成本极低，建议纳入路线图）

已有 `/` 语法可用（`ui/index.html`）。若要更顺手，可加**前缀修饰符**，零索引成本：

| 语法 | 含义 | 实现成本 |
|---|---|---|
| `ui/index.html` | 已支持：含 `/` 即按路径打分 | **0**（已完成） |
| `dir:ui index.html` 或 `>ui index.html` | 任意词可标记为"只筛目录" | 小（查询解析） |
| `@dir` | 同上 | 小 |

这类语法**不增加任何索引体积**，也不改变默认行为，语义明确无歧义。

### 5.3 若一定要做自动版本

唯一相对安全的做法是**降权而非强制**：目录命中给一个介于 `PATH_ASSISTED`(1<<14) 与 `NAME`(1<<16) 之间的档位（如 1<<15），让"命中目录"比"散落在 basename"更优但**不淘汰** basename 命中。需再实测一轮确认不劣化 `game_scene lua` 等用例。体积代价 +4.2 MB（目录名集合）。

## 6. 体积性价比总结

| 方案 | 增量体积 | 每条目 | 收益 | 建议 |
|---|---|---|---|---|
| 显式 `/` 语法 | **+0** | 0 | 目录筛选可用 | ✅ 已有 |
| 显式 `dir:` 前缀 | **+0** | 0 | 更顺手 | ✅ 推荐 |
| 目录名集合 + 降权 | +4.2 MB (+18%) | 86 B | 有限 | ⚠️ 需再验证 |
| 目录名集合 + 强制 | +4.2 MB | 86 B | 净负（劣化 3 例） | ❌ 否决 |
| trigram 预筛 | +9.4 MB (+41%) | 193 B | 提速，非功能 | ⚠️ 当前 7.4ms 无需 |
| 子词边界位图 | +108 MB (+470%) | 2,214 B | — | ❌ 否决 |

**当前索引 ~23 MB / 51k 条目本身是合理的**（460 B/条目，字符串占 88%）。唯一值得做的体积优化是**去掉 `pathLower` 重复副本**（可省 ~9 MB / 39%），代价是每次查询多一次 `toLowerCase`——但查询要扫全表，反而变慢，故**也不建议**。
